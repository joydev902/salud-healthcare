# Work queue performance

Generated by `python run.py bench` (`backend/scripts/benchmark.py`). Synthetic data only.

## Dataset

| | |
|---|---|
| members | 24,983 |
| opportunities | 163,093 |
| source rows | 200,000 |
| providers | 40 |
| PostgreSQL | 17.11 |
| Host | Windows 11, Python 3.13.16 |
| Import time | 277.4 s across all uploads (721 rows/s through the ingestion service) |

The coder is assigned one provider group (5 of 40 providers, ~12% of the data); the
admin is assigned all providers. ~35% of opportunities carry a decision.

## Timings

Service-level latency (SQL + Python), 15 runs after 3 warm-up runs, page size 25.

### How to read this

- Default and deep pages use a nested-loop semi-join on
  `uq_members_external_member_id` + `uq_opportunity_business_key`. Page 201 is as
  cheap as page 1 (no OFFSET walk).
- Initiative filters probe `ix_source_opportunity_initiative` (index-only). The
  Screenings ∩ Denied case dropped from ~125 ms / 10k disk reads (hash-aggregate
  over every Denied row) to ~19 ms / 4.6k buffer hits after that covering index.
- Member search (`ILIKE '%term%'`) is the remaining outlier. Trigram GIN indexes
  are installed; a dedicated `lower(external_member_id) text_pattern_ops` index
  would help prefix lookups like `SYN0012%` further.
